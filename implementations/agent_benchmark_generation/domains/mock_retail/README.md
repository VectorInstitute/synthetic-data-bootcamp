## Tasks
Each task has three parts: 1) task description and type 2) user_scenario passed to the user simulator, and 3) evaluation_criteria used by the scoring pipeline to score the agents

agents will not see `user_scenario.instructions` and `task.description` because they should be able to infer the user intent from the conversation.

 --> "id": a unique string used as the task ID,
 --> "description": a string that describes the purpose of the task. high-level description of the **evaluation task goal**. Must match Constraints.task_type (and policy)
 --> "task_type": each domain has a set of task types. this helps define the FSM for task validation, and also these task types are used to increase diversity. Before generation, a specific task type if sampled, so that the generator is conditioned to generate a reasonable task ang not anything that it wants (increased fidelity)

--> "user_scenario": these values are passed to the user simulator
       --> "user_name": first and last name of the user,
       -->"personality_style": user's personality as a string. personality styles are defined in `user_simulator.yaml`
       --> "instructions": a brief that guides the **user simulator LLM** toward this
  specific task instance. Include {cfg.id_field} {primary_id} and any other args the
  oracle needs (addresses, etc.). Only instructions (not description) carries these
  user-specific details. No personality theatrics. Must be consistent with
  description/task_type and the oracle actions. Not shown to the agent under test. The goal is to make sure that user simulator knows its order and order id, so the `order_id` field is passed to the user simulator (`cfg.id_field`: `primary_id`).
    -->"initial_message": the first message that is sent by the user to the agent(s). first customer utterance written **in the sampled personality style**. Prefer **partial disclosure** so multi-turn dialogue is needed.


--> "evaluation_criteria":
        "actions": ground truth (Oracle) actions that directly result in the final DB. The final DB is generated by replaying these actions on the original DB. This is usually the easiest (shortest) path to the final DB because the generator LLM knows the user instructions (ids/args), therefore it has access to more information than the agents which can mean an easier job for the evaluator compared to the system being evaluated. ### Sample Constraints
Before generating any task, an existing task is sampled and a few of its features are used to guide a guided generation. First a task_type is sampled from the FSM. then all the collections are fetched from the db (in the retail domain, collection is the orders table (defined by `primary_collection` in generation.yaml)). Then, an item of the collection (here an order) is randomly selected. Are the entities related to that order are also fetched (using the order id). The relation between the child and parent table is defined under the `related` field in `generation.yaml`. The extracted related entities of the primarly item (order) are passed as `entity_context` to the generator prompt.


a personality_style is also drawn from user_simulator.yaml
